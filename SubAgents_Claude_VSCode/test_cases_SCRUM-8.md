## Coverage Notes

- **AC1** (successful login redirects to Patient Dashboard): **TC-01** (primary happy path), supported by **TC-02** (email-casing variant of the happy path).
- **AC2** (valid username/email + invalid password → generic error, stays on login page): **TC-03** (primary case), reinforced by **TC-05** (both fields wrong) and validated for parity in **TC-06**.
- **AC3** (invalid username/email → SAME generic error as AC2, no enumeration): **TC-04** (primary case), reinforced by **TC-05**, and explicitly proven identical to AC2 in **TC-06** (the dedicated anti-enumeration comparison case).
- **AC4** (empty required field(s) → field-level validation, submission blocked): **TC-07** (both empty), **TC-08** (username empty only), **TC-09** (password empty only), and **TC-10** (whitespace-only treated as effectively empty/invalid).

## Suggested Additional Coverage

- **Browser/device matrix**: Re-run TC-01, TC-03/TC-04, and TC-07 across the supported browser set (Chromium/Firefox/WebKit per the project's pytest/Playwright config) and at common responsive breakpoints (mobile/tablet/desktop), since the login page is the portal's front door.
- **Copy-paste credential entry**: Verify pasting credentials into both fields (e.g., from a password manager) works identically to typing, and that paste is not blocked on the password field (a common accessibility anti-pattern).
- **Browser autofill / password manager integration**: Confirm the fields expose correct `autocomplete` attributes (`username`, `current-password`) so browser/OS password managers can offer to save and fill credentials, and that autofilled values pass validation/submission the same as typed ones.
- **Network failure / slow API response handling**: Simulate a timeout or 5xx from the authentication API (e.g., via Playwright route interception) and confirm the UI shows a distinct "something went wrong, please try again" message rather than the credential-specific generic error — and that the Log In button is disabled/shows a loading state during the request to prevent double submission.
- **Double-submit / rapid repeated clicks**: Click **Log In** multiple times in quick succession with valid credentials and confirm only one authentication request fires and only one redirect occurs (no duplicate session creation).
- **"Remember me" / persistent session option** (if present on the login page): Confirm its behaviour on subsequent visits, and that it does not weaken the generic-error/anti-enumeration guarantees.
- **Concurrent session behaviour**: Log the same patient in from two different browsers/devices simultaneously and confirm the expected policy (both allowed, or second login invalidates the first) — relevant to HIPAA session-management expectations even though full session-timeout testing is out of scope here.
- **Locale / internationalization of error and validation text**: If the portal supports multiple languages, confirm the AC2/AC3 generic message and AC4 field-level messages are translated consistently and remain identical to each other in every supported locale (enumeration-safety must hold across locales too).
- **Audit logging of login attempts**: Confirm (at a system/log level, not UI) that both successful and failed login attempts are recorded with timestamp and outcome — a common HIPAA-adjacent compliance expectation — without logging plaintext passwords.
- **Clipboard/devtools leakage check**: Confirm the password value is never present in plaintext in page HTML source, browser history, or client-side JavaScript variables accessible via the console after submission.
