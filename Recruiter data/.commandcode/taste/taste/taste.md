# Taste
- Prefers Python + MongoDB for backend data storage when building React apps (instead of e.g. Node/Postgres or a paid cloud backend). Confidence: 0.9
- Prefers free / self-hosted / open-source solutions over paid services or paid hosting ("for free" when describing storage). Confidence: 0.6
- Uses Vercel as the hosting/deployment platform for the frontend, with the app's API served as Vercel serverless functions (an `api/` directory) backed by MongoDB — expects deployments to be carried out and verified to completion (build, deploy, then check the live URL and API endpoints). Confidence: 0.6
- Prefers one-click batch scripts (e.g. `start-mongo.bat`, `start-backend.bat`, `start-frontend.bat`) to start the dev stack, and asks the assistant to run those scripts rather than raw commands. Confidence: 0.5
- Wants applications to have a professional, polished UI (asks for a "professional template" rather than a generic/default look) and expects visual design to be synced with the app's UI. Confidence: 0.7
- Has a strong, particular aesthetic sense for UI: will explicitly reject a restyle and demand further changes until the look matches their taste ("Change the UI still i am not liking it") — expects iterative visual revisions, not a one-shot restyle. Confidence: 0.7
- Chose a "modern colorful" visual direction for the dashboard: gradient header, glassy rounded cards, soft shadows, vibrant avatars and badges, friendly modern consumer feel. Confidence: 0.8
- Prefers data/dashboards to be always visible inline (e.g. status breakdown shown directly in each recruiter card) rather than hidden behind clicks or interactions. Explicitly rejected a click-to-reveal design in favor of an at-a-glance layout. Confidence: 0.7
- Wants duplicate validation / data hygiene enforced at the data-entry points: Excel uploads should reject files containing duplicate candidate rows (matched on phone + email), and adding entities (e.g. recruiters) should prevent duplicates. Confidence: 0.7
- Communicates in short, informal, sometimes ungrammatical feature requests and bug reports (e.g. "Export to excel count is not getting updated once the excel is uploaded", "Make Sure There is no data loss") and expects the assistant to flesh out the details and deliver a complete, verified end-to-end solution (backend + frontend + tests + docs). Confidence: 0.75
- When requesting removal of UI features (e.g. deleting tabs/views), explicitly demands that no data be lost ("Make Sure There is no data loss") — expects the assistant to verify the underlying data/rendering is unaffected before removing anything. Confidence: 0.6
- Wants full CRUD symmetry for managed entities: anything that can be added through the UI (e.g. recruiters) should also be removable from the UI, not only via backend/API calls. Confidence: 0.7
- Expects the locally running app to be reloaded/restarted so code changes are actually live at the local URL — after changes, the assistant should restart the dev stack (killing orphaned processes on the ports first) and verify the new behavior end-to-end in the running app, not just leave the code updated. Confidence: 0.7
- Prefers auto-save editing and live data sync: changing a value (e.g. candidate status via a dropdown) should save immediately without a submit button and instantly propagate to every view — the table row, the detail popup, and the per-recruiter breakdowns/KPIs on the main screen — with no manual refresh. Also expects displayed counts (e.g. the export count) to update automatically after a data-changing operation like an Excel upload; stale numbers after a mutation are bugs. Confidence: 0.9
- Wants the app to export data back to Excel (same column layout as the upload format), not just accept uploads — Excel is the round-trip data interchange format for this app. Confidence: 0.6
- Specifies exact UI requirements by referencing screenshots (by filename or description, e.g. "the Candidate list image from data", "the Tabular Header not seen image under Data folder") and expects the assistant to inspect them and implement precisely what is shown. Confidence: 0.9
- Treats the same metric appearing in multiple views/sections as data that must agree: when a count (e.g. the Clients KPI) diverges from an equivalent breakdown elsewhere (e.g. the Sources of Applications donut), that is a bug to fix by deriving both from a single source of truth rather than two independently-computed numbers. Confidence: 0.7
- Wants summary/stat KPI cards to be clickable drill-down entry points: clicking a stat (e.g. Clients) should open a modal grouping the underlying records by that dimension (each group showing names + status badges), with links that drill further into individual record details. Confidence: 0.6
- Prefers drill-down navigation via clickable hyperlinks in table cells: candidate names open a detail popup, and client names open a popup listing that client's candidates (name + status) with drill-through into individual candidates. Expects the same hyperlink pattern applied consistently to all comparable columns. Explicitly re-verified: clicking a client link in a popup must show that client's candidate names and status details. Confidence: 0.9
- When drilling down from one popup into another (e.g. clicking a client link inside the Clients popup), the next level must be immediately visible — stacked modals where the parent popup's backdrop covers the child popup are bugs; the parent popup should close when the drill-down opens. Confidence: 0.6
- Prefers pagination over long scrolling lists in popups: when a drill-down list (e.g. a client's candidates) may not fit on screen at the current resolution, use paging (~10 items per page) instead of an unbounded scroll. Pagination must be interactive and actually update while navigating: clickable page-number buttons with the active page highlighted (with ellipsis when there are many pages), not just Prev/Next plus a static "Page X of Y" readout — a pagination display that doesn't update is a bug ("pagination links are not updated"). Confidence: 0.8
- Popups/modals must keep all content reachable regardless of viewport height: a modal should be height-capped to the viewport and scroll internally (overflow-y) so lower rows and pagination stay visible — a popup that is "static" and cuts off content while the page behind scrolls instead is a bug. Confidence: 0.7
- Wants the assistant to ask clarifying questions before implementing ambiguous feature requests ("Any clarifications ask me before proceeding") and answers the posed options directly rather than leaving decisions open. Confidence: 0.7
- Tracks previously explained requirements and explicitly follows up when one is missing ("Hyperlink is not provided for clients tab as explained before") — expects every earlier request to be implemented, not just the latest one. Confidence: 0.6
- Wants dropdown option lists (e.g. candidate Status values) applied consistently across the entire application, and expects the implementation to work end-to-end: the backend must accept the new values without API errors when selected, and the dashboard/KPIs must reflect the selection — new UI options are not complete if they only render in the dropdown. Confidence: 0.6
- Maintains multiple sibling apps in the same repo with parallel status vocabularies ('Recruiter data' and 'Interview Tracker' on different ports); a request phrased "across the Application" can mean all of them — when the wrong app was edited first, the user explicitly chose "Both apps" — so shared dropdown values/features must be applied to every app in the repo, and the assistant should confirm which app the user is actually viewing (check running dev servers/ports) before editing. Confidence: 0.7
- Wants the dashboard to include analytics charts (pipeline bars, decision/source donuts, applications-by-month line chart, vacancy/fill-rate stats) as shown in the reference template, driven by the app's real data rather than mock data. Confidence: 0.6
- Cares about alignment/visual polish of wide data tables: wide multi-column tables must be properly aligned and navigable — sticky column headers, pinned key identifier columns (e.g. Candidate, Client) while scrolling horizontally, a bounded scrollable height, and consistent column spacing so headers never drift out of view relative to data. Confidence: 0.7
- Prefers data tables rendered with full grid borders — visible vertical separators between columns (border on both header and body cells, border-collapse: collapse) rather than minimal styling with only bottom row dividers ("Make the Tabular columns with the Table borders"). Confidence: 0.6
- Prefers data-table headers to be dark/themed — navy background with white column-name text matching the app's theme color (--navy, same as the topbar) instead of a light gray header ("Make the Tabular heading with Darker Column Name"). Confidence: 0.5
- Cares about the production URL being clean and shareable: asked to change the app's auto-generated random-suffix Vercel URL (`recruiter-tracker-fawn.vercel.app`) to a more concise/clean alias, and expects the deployed app to be publicly accessible at that tidy URL (not login/SSO-gated). Confidence: 0.4
- Wants data mutations to be auditable: explicitly requested a "Transaction History Logs" feature so every status change on a record is recorded (who, when, from→to status) and viewable in the UI, not just silently persisted. Confidence: 0.5
- Wants dashboard time-period filters (month/year) to drive the entire dashboard consistently — KPIs, recruiter stats/cards, charts, and the underlying candidate detail table must all regenerate from the selected month/year, and changing the year must change the candidate details shown for that month. A filter that only affects summary numbers while leaving detail data stale is a bug. Confidence: 0.65
- Actively re-verifies reported fixes himself (clears browser cache, hard-refreshes, rechecks the running/deployed app) and reports back with "still showing the old values" if the problem persists — expects the assistant to keep diagnosing (checking what is actually being served/deployed, looking for duplicate copies) rather than treating the report as a cache fluke. Confidence: 0.5
